# Agent Documentation Rules

This file is the canonical reference for the repository's documentation
policy. The root `AGENTS.md` reads it for the full ruleset; the summary
in `AGENTS.md` is the daily read.

## 1. Three categories

Documents are classified by lifecycle and authority, not by author:

- **Canonical** in `docs/` describes how the system works today.
- **Working state** in `.agent/tasks/` describes how a particular task
  was performed; it is not authoritative.
- **Generated artifacts** in `artifacts/reports/` describe the output of
  a specific point-in-time operation.

## 2. Where to put each kind of file

| Kind                                                   | Path                                                            |
| ------------------------------------------------------ | --------------------------------------------------------------- |
| Current architecture / contracts / wiring              | `docs/architecture/`, `docs/api/`                               |
| Developer workflow, conventions, run-rules             | `docs/development/`                                             |
| Deployment, operations, runbooks                       | `docs/operations/`                                              |
| Long-term architectural decisions                      | `docs/adr/ADR-NNN-*.md`                                         |
| Non-trivial Agent task                                 | `.agent/tasks/<id>/{context,plan,research,decisions,result}.md` |
| Dated reports (audits, contract diffs, perf baselines) | `artifacts/reports/YYYY-MM-DD-*.md`                             |
| Throwaway analysis, debugging, prompts                 | `.agent/scratch/` (gitignored)                                  |

## 3. Source-of-truth rule

`code` ≥ `tests` > `docs/adr/` > `docs/` > `artifacts/` > `.agent/`.

`.agent/` is **not** a source of truth. A future developer must be able
to understand the system from `docs/`, the code, the schemas, and the
tests — without ever reading an Agent task workspace.

## 4. Task lifecycle

1. Inspect relevant code, canonical docs, ADRs, prior `.agent/tasks/`
   context.
2. Create a task workspace: `.agent/tasks/<id>/`.
3. Fill in `context.md` and `plan.md` for non-trivial work; record
   investigation in `research.md`; capture decisions in `decisions.md`.
4. Promote durable knowledge into `docs/` or an ADR before closing the
   task. Move completed tasks to `.agent/archive/` or delete them.
5. Write `result.md` summarising what changed and what was tested.

## 5. Promotion rubric

- A discovery with no long-term value: keep only in `.agent/`.
- A change to system behaviour: update `docs/architecture/` or `docs/api/`.
- A long-term decision: write `docs/adr/ADR-NNN-*.md`.
- A change to developer or deployment workflow: update
  `docs/development/` or `docs/operations/`.

## 6. Do not pollute

Do not place task notes, plans, investigations, or Agent scratch into
`docs/`, `README.md`, source directories, or the repository root.
Avoid filenames such as `analysis.md`, `notes.md`, `plan.md`, `todo.md`,
`agent-notes.md`, `implementation-notes.md` at the repository root.

## 7. Naming

- Canonical docs: `kebab-case.md`.
- ADRs: `ADR-NNN-*.md` with `NNN` zero-padded.
- Task workspaces: `.agent/tasks/<ticket-or-kebab-case>/`.
- Reports: `artifacts/reports/YYYY-MM-DD-*.md` (or `vX-*.md`).

## 8. Generated files

If a documentation file is generated by a tool, mark it:

    <!-- Generated file. Do not edit manually. -->

…and document the generator in the file or its manifest.
