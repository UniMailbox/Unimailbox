# Unimailbox 1.0.1

MCP access for local agents and lower routine KV usage for rebuilt installations.
Updating source does not deploy an installation or change its mail routing.

## Changes

- Add the MCP service card under Admin → AI services, with one service switch
  and a shared editable setup prompt. Users create their own expiring,
  mailbox-scoped credentials in Quick settings. Read, draft/AI and send grants
  remain bounded by current account and mailbox permissions.
- Keep credential revocation available while MCP is disabled. Add explicit
  pagination for older credentials while preserving cached clients during upgrades. Existing account-bound one-time secret
  handling remains in place. Issuance and Copy prompt remain gated by the service switch. MCP
  initialize now reports the product version.
- Remove MCP polling and its redundant browser-token KV lookup. Reuse browser
  identity descriptors for 60 seconds; server authorization remains live.
  Unauthenticated/repeated logout avoids unnecessary KV deletes.
- Persist maintenance heartbeat and failure snapshots in D1 with atomic task
  state, one-time legacy handover and freshness/failure checks. This removes
  313 fixed KV writes/day per installation and three KV reads per steady
  maintenance health probe. Existing schedules and other KV caches remain.

## Upgrade

Read the [update guide](../operations/updates.md) and
[deployment/recovery runbook](../operations/deploy.md). Preserve local fork
changes, account/resource identities, encryption keys and private forwarding
settings. Back up D1 and R2 before upgrading; do not repeat bootstrap or setup.

Compared with 1.0.0, rebuilt installations apply additive migrations 0035–0037
through the canonical release command and verify all 37 SQL companions.
MCP starts disabled; upgrading does not grant agent access or enable sending.
Existing heartbeat state is adopted once from KV, including recorded failures;
old keys expire under their original TTL. Subsequent monitoring uses D1.

Older Workers require their exact schema version for readiness. Blind code
rollback after migration is not a healthy recovery; use a reviewed compatible
build or coordinated database/object/key recovery. Never delete migration
history or replace an encryption key to bypass a failed check. The legacy mail
application uses a different schema and must not receive this migration chain.

## Verification and limits

The release requires the complete local/GitHub verification gates and matching
main/tag/product version. Review findings and exact deployment/runtime results
are recorded in [1.0.1 QA](../qa/release-1.0.1-2026-10-15.md).
Local fixtures and bounded live checks do not replace the full mail/attachment
acceptance catalog or a full post-release quota day. Existing production mail
routing, keys and configuration are retained; AI/MCP are not enabled by rollout.

MCP `confirmed=true` records the agent's assertion of human approval; it does
not independently prove approval. Use read/draft-only grants when stronger human
control is needed. Copy prompt never contains a credential. Credential limits,
Origin checks and auditing do not replace account-level network abuse controls.

Pre-existing dependency advisories remain: the October 15 audit reports one
critical, 13 high, 18 moderate and four low findings across development/test,
router/sanitizer and other transitive packages. The MCP dependencies added in
this PR are not named in those advisories. This is dependency metadata, not an
exploitability assessment or security clearance. Broad dependency upgrades are
separate from these scoped fixes; see the dated QA record for audit boundaries.
