# CAP-038 — Remove deprecated `INVALID_REQUEST` catalog entry

> The shared contract for this capability. Every agent working on it reads this file first.
> Location: `work/active/CAP-038-remove-invalid-request/task.md`.

**Phase:** 2 · **Status:** In Progress · **Started:** 2026-08-15

## Goal

Close out the CAP-032 migration window by removing `INVALID_REQUEST` from the
closed error catalog, so the union of `ErrorCode` no longer carries a code that
no route or module emits. After this slice, the catalog reflects what the
system actually emits today.

## Scope

**In scope:**

1. **Catalog deletion.** Remove `INVALID_REQUEST: 'INVALID_REQUEST'` from
   `ERROR_CODES` in `apps/worker/src/platform/errors.ts:55` and the preceding
   "Deprecated — migration window only; remove in a follow-up capability."
   comment at `:54`.
2. **Comment cleanup.** Remove the "3. **Deprecated** — `INVALID_REQUEST` is
   being phased out ..." bullet (`:19-23`) of the catalog header comment in
   `apps/worker/src/platform/errors.ts`. The catalog has two buckets, not three.
3. **`EmittableErrorCode` narrowing collapsed.** Delete the
   `EmittableErrorCode = Exclude<ErrorCode, 'INVALID_REQUEST'>` type alias at
   `apps/worker/src/http/middleware/error.ts:28-34` and inline `ErrorCode` at
   its three call sites (`:52` `envelope()` parameter; `:81-92` `DomainError`
   branch).
4. **Runtime narrowing removed.** Delete the `err.code === 'INVALID_REQUEST' ?
   'VALIDATION_ERROR' : err.code` ternary at
   `apps/worker/src/http/middleware/error.ts:89-90` and the preceding comment
   block at `:82-88`. With the alias gone, `err.code` is already `ErrorCode`
   (which no longer contains `INVALID_REQUEST`).
5. **Test update.** Remove the `INVALID_REQUEST` assertion and comment in
   `apps/worker/src/platform/errors.test.ts:55,58`. The "documented
   migration-window" test no longer has a deprecated code to assert.

**Out of scope:**

- **Success-envelope changes.** Already uniform.
- **`INVALID_REQUEST` removal from build artifacts** (`apps/worker/dist/**`).
  Generated by `pnpm build`; will regenerate as part of the gate run.
- **Catalog additions for new codes.** No new codes are introduced in this
  slice.
- **Generalising the deprecation pattern.** No site today needs a
  "two-step" removal like this one had. The capability is recorded as
  precedent if a future code follows the same path.

## Risks

- **Catalog churn for downstream consumers.** `INVALID_REQUEST` has been in
  the catalog since CAP-032 landed (today). Removing it tightens the union,
  which is exactly the intent — but any test, mock, or downstream caller
  that referenced `INVALID_REQUEST` by name would fail to compile. The
  implementer runs `pnpm typecheck` after the catalog deletion and reports
  any unexpected failures as BLOCKER findings in the handoff. The full
  pre-slice grep showed only the three intentional sites in source; the
  `dist/` artifacts are regenerated by `pnpm build` and are not committed.
- **`@ts-expect-error` test drift.** The AC3 demo in `errors.test.ts:27-28`
  uses `'R-AUTHZ-004'`, not `INVALID_REQUEST`, so it is unaffected. The
  implementer verifies by reading the test before deleting anything in
  `errors.test.ts`.
- **Comment-staleness creep.** The header comment in `errors.ts` currently
  describes three buckets (live, catalogued-but-unused, deprecated). After
  the slice, only two buckets remain. The implementer updates the comment
  to reflect the post-slice state, not just deletes the deprecated bullet.
