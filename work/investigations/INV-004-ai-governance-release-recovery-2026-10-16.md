## 4. AI 治理方案

### 4.1 额度语义

1. 安装级为该安装全部 AI 请求总额；用户级归属已认证 userId，网页/MCP/未来入口共用。共享邮箱也计入实际发起用户；服务账号必须显式归属，禁止空身份绕过。
2. 建议首期以 **UTC 自然月**为主要额度周期，配合每日保护上限；周期、总额和默认用户额是待配置策略，不在本轮拍定数值。零额度表示禁止；未配置、无限额和继承必须是不同状态。
3. 全部输入 token（包含缓存输入，去重后计一次）与输出 token 为配额单位；reasoning 若已包含输出总量，不能重复相加。保留原始分类的数字证据以解释价格差异，不存提示词。
4. 三协议 token 总和用作治理单位，不宣称不同模型的 token 等价于相同费用。价格按模型/端点/币种/生效日期记录；未知价格显示“未配置”，费用不置零，不做账单承诺。
5. 同时满足安装、用户、各启用周期、单请求和并发约束才准入。用户额总和可大于安装额，但 UI 要说明总池仍是上限。
6. 额度下降不撤销已提交请求；剩余额可为零并显示超出部分。模型/价格/策略修改不改写历史 attempt，记录配置修订和快照。

准入模型：`本期已结算 + 本期预占/未知占用 + 本次输入预占 + 本次最大输出 <= 本期额度`。
准入按请求开始时的周期归属；跨日/月完成仍结算原周期，不通过每日清零释放旧请求。活动/未知并发跨周期继续计入。

### 4.2 发送前输入预算与能力档案

- 在最终提示词组合后、服务商调用前，统一计算 system、messages、引用邮件、模板和 JSON Schema 等输入；先限制总 UTF-8 字节、消息数、schema 大小/深度，再计算 token，避免计数自身无界耗时。
- 邮件原文可以按明确策略缩短，并显示上下文被截断；用户指令不能静默丢弃。缩短后重新计数。单请求输入预算还必须满足模型上下文窗口减去输出上限和协议开销。
- 建立按 `protocol + endpoint + model/revision` 的能力档案：计数方法/版本、保守上界依据、上下文窗口、输出限制是否生效、usage 字段、查询/取消能力、价格来源及验证日期。endpoint 使用安全标识，不记录凭据。
- **本地账本硬准入**与**真实服务商 token 不超限**分别验收。字符/4、未经证明的安全系数、未验证的兼容端点不能支持后一项承诺。精确 tokenizer 仍需计入服务商消息封装开销；计数 API 的误差也需有上界依据。
- 严格模式只接纳有可信保守上界且输出上限已验证的模型。无法给出可信上界时，明确拒绝该模型进入严格模式；可提供显式标注的观察模式供验收，不能把观察模式称为硬限制已生效。
- 如果实际用量超出预占，保留真实消耗并停止该模型的新准入，触发能力档案失效告警；不得把数字裁剪为预占值掩盖超额。
- 计数接口本身也设超时、限流和最大并发；失效时严格模式拒绝准入，不回退到无界推理。

### 4.3 独立尝试记录、结算和并发

建议由 AI 模块拥有策略、attempt 和计数持久化；Admin 负责权限、策略编辑投影与审计注入；组合入口连接配置读取和模块，不建立 AI → Admin 持久化的循环依赖。适配器只负责协议事实，messages 用例保留邮件授权与提示词组装。

建议新增的逻辑记录（表名/迁移号在实施时分配）：

| 记录 | 最小内容 |
| --- | --- |
| 策略/周期额度 | 安装或用户 scope、周期、上限、版本、已结算/预占计数、并发阈值 |
| AI attempt | 服务端 attemptId、用户、操作/幂等关联、配置和策略修订、模型能力版本、状态、输入预占/输出上限、时间戳、provider request/completion ID（取得时） |
| 用量结算 | attempt 唯一键、真实/保守计费分类、input/output/cache/reasoning 数字、usage 完整度、未知占用、价格版本、结算证据类型、审计关联 |
| 运维修正 | 核对或手工调整的理由、证据摘要、操作者、前后数值；追加记录，不覆盖原事实 |

主状态建议为：`reserved → submitted → completed / rejected / outcome_unknown`；内容结果（可用/拒答/校验失败）与计费证据（已知/缺失/待核对）分开。

- 授权和输入校验后，在同一 D1 原子事务内完成幂等唯一预占、两级额度预占和并发准入；同 key 并发不能计费两次，安装和用户竞争不能只扣一边。SQL 全部受同一准入决定约束；禁止先 SELECT 再无条件 UPDATE。
- 任何上游 I/O 前持久化 submitted。崩溃落在标记之后、网络之前也保守归未知，不能用“本地没有结果”推断未执行。预占/提交记录写失败则禁止调用。
- 收到服务商响应后先保存用量和执行事实，再做最终文本/JSON 业务校验；拒答、输出截断或不合法内容仍需计入消耗。
- 结算、额度变更和审计保持原子，按 attempt 幂等；重复返回、迟到返回、核对任务竞争均只结算一次。结算失败保留占用和待修复状态，不二次生成。
- 活动租约仅表示本地执行者是否存活。租约过期、HTTP 超时、网页关闭不能释放未知计费预占；未取得终态也不能声称上游并发已释放。
- 安装级/用户级并发在 D1 跨 isolate 生效；未知在途单独计数并占安全容量，达到阈值时阻断新调用。运维可通过有证据核对恢复容量；无证据强制解除必须是显式、有审计的风险覆盖，不能自动按时间解除。
- 建议先保留同步生成。迟到回调可尽力结算，但持久账本必须在回调永不执行时仍正确；首期恢复器只核对/保守挂账，不自动重发推理。确有长任务需要时再评估持久异步执行。

### 4.4 未知结果、幂等与用户行为

- 超时/网络断开/上游响应解析失败：只要可能提交过，就记 outcome_unknown。明确“未执行”的证据才可释放全部预占；明确终态但缺 usage 时仍保留 token 上界占用，不能记零。
- UI 关闭文案表示“停止等待，处理和计费可能仍继续”。状态查询读取已有 attempt；同一操作在刷新、重开、查询、重试连接时沿用 key/attempt。重新生成是显式新操作，需重新准入并提示可能再次消耗。
- 24 小时重放正文可按现有隐私策略过期；attempt 身份、未知占用和去重墓碑独立保留。建议生成 key 带可验证创建时间并限定新请求受理窗口，旧 key 到期后只能查既有记录或返回过期，不能重新生成。迁移前的历史 key/未知记录保守隔离并列明能力边界。
- 核对优先使用已拿到的 provider ID 和服务商正式查询能力；没有单请求核对接口时保持未知，可按可靠上界保守计入额度并标记估算。账单总量不能随意分摊成某用户的真实用量。
- 不默认开启上游内容保存、全量日志或新计费服务。OpenAI Responses 的后台取消接口不作为当前 Chat Completions 的取消保证。
- 本地额度严格控制本应用的准入；其他应用共用同一服务商 key 的消费不在本地额度范围，需在 UI 明示。

## 5. 兼容性发布门槛

1. 冻结已发布 v1.0.1 的关键 schema/响应和一个旧 Web 构建，保存源 revision 与文件摘要；测试不能导入当前 schema 后再 omit 来充当唯一历史真值。
2. 覆盖 MCP 个人设置的旧严格结构、分页协商头未知值、AI 配置、生成回复、错误 envelope、鉴权/刷新和关键列表。每次公共契约变动需列出受影响的旧消费者。
3. 矩阵最少包含“旧客户端 + 新 API”“新客户端 + 新 API”“新客户端 + 上一版 API（回滚/混部窗口）”；MCP 另用固定 SDK/协议版本验证 initialize、tools/list、tools/call 和错误，缓存 Web 客户端与 MCP 协议客户端分开验收。
4. AI 用量/策略/attempt 查询优先新增独立端点；旧 strict 配置/生成结果结构保持兼容。确需改变生成返回、错误码枚举或状态码时先设计能力协商/新版本；旧客户端必须可理解失败且不自动付费重试。
5. 迁移使用 expand → 兼容读写 → 数据迁移 → 延后清理。回滚到不认识额度的新旧 Worker 会绕过治理，因此**schema 可读不等于治理可回滚**；切换到旧代码前必须通过快照之外的控制关闭 AI 新请求，确认所有入口都生效。
6. 保留现有 source/tree/schema/asset smoke；补旧缓存页面在发布后访问的浏览器场景、旧静态 chunk 生命周期、按需刷新提示和混部失败行为。不能只验证首页 JS 存在。
7. 本地契约/迁移矩阵纳入 pnpm verify；发布草稿前形成机器可读报告。真正发布门槛还需目标安装的 smoke、相应变更的回滚证据，以及涉及持久化语义时的隔离恢复报告。普通 UI 发布无需每次重做全量灾备，但必须有有效的基线证据。

## 6. 可观测性与管理界面

继续使用已有平台/邮件两个区域；AI 用量做独立卡片或页面，避免把估算费用混入 Cloudflare 官方用量。需要新增指标的定义如下：

| 指标 | 定义与展示约束 |
| --- | --- |
| 额度 | 按安装/用户/周期显示已结算、预占、未知占用、剩余和重置时间；真实 token 与保守估算分开 |
| 并发 | 正在执行、结果未知、安全阈值、拒绝次数；用户只可见自己的额度，管理员查看安装及用户汇总 |
| AI 时延 | 准入等待、上游往返、首次提交至本地结算分别计；超时和未知数单列，不能只用成功样本掩盖失败 |
| 入站时延 | 本地接收至持久处理完成；不宣称为发件人点击发送至到达时间 |
| 出站时延 | 就绪时间 max(created_at, scheduled_at) 至服务商确认接收；另列计划等待和 provider callback 交付时延，不把 accepted 当 delivered |
| 恢复耗时 | 首次确认故障/过期租约至恢复终态，及最老未恢复年龄；原始时间戳不可由任意 updated_at 替代 |
| 备份/演练 | 最近成功一致恢复点、备份完成/延迟、失败原因、对象核验覆盖、演练实测 RPO/RTO；没有证据显示“未验证” |

长期趋势采用有界的不可变完成事件/聚合，避免继续从短期 receipt 的现存行反推历史。按 UTC 小时/日聚合，保留样本数与未结任务；P95 用原始有界样本或可合并直方图计算，不能平均各日 P95；不足预设样本门槛不显示稳定 P95。建议原始无正文事件保留 30 天、日聚合 180 天，已结 AI 账本至少覆盖当前/上一周期和审计保留要求；这些期限在容量测算后确定。未核对 attempt 不按普通 TTL 清理，需单独积压上限和告警。

不采集邮件正文、附件字节、提示词或生成正文到监控；不增加敏感用户标签的高基数全量日志。先测每请求新增 D1 读写/延迟、日行数、保留容量与查询计划，再扩图表。计费账本写入失败必须阻止不受控调用；展示用遥测失败不能破坏邮件主流程。

## 7. 备份恢复目标和成本权衡

RPO 是可接受丢失的数据时间范围；RTO 是从事故开始到约定业务恢复的时间，包含发现、决策、取回密钥、导入、校验和切换。下面是**建议目标，尚未实测**，按单安装故障/误操作考虑，不代表平台级灾难同样达标。

| 档位 | 完整 D1 + R2 一致恢复点 RPO | 完整服务 RTO | 建议机制与成本 |
| --- | --- | --- | --- |
| 基础 | ≤24 小时 | ≤8 小时 | 每日加密 D1 导出与增量对象副本、清单、离线密钥；存储/请求成本较低，但邮件损失窗口大 |
| **推荐** | **≤1 小时** | **≤4 小时** | 小时级协调检查点与对象增量保护，独立备份权限/保留旧对象、每日校验、每季度隔离演练；增加导出负载、对象请求、保留容量和运维投入 |
| 强化 | ≤15 分钟 | ≤1 小时 | 持续增量保护/变更记录、预建隔离恢复设施、更频繁演练与检测；成本和实现复杂度最高，需测数据规模和跨存储一致性 |

建议首期选推荐档作为工程验收方向，并为“账号不可访问/平台大范围故障”单列 **RPO≤24 小时、RTO≤24 小时的异地/异账号恢复候选目标**。这要求独立控制面和凭据；若备份仍与业务共用账号及权限，则不宣称覆盖账号失陷。真实保障以演练数据修订，不能单凭 D1 分钟级恢复能力推导整套邮件服务 RPO。

小时调度并不自动保证一小时 RPO：有效恢复点是 D1 引用的所有必要对象和匹配密钥均已保护的最后检查点，其年龄包含调度延迟、导出和复制耗时。必须缩短实际调度间隔或采用增量设计，留出这些耗时余量，并监控检查点年龄。若对象备份失败，该点不算成功。

费用先按数据量测算，暂不承诺金额：`D1 导出/校验读写 + 完整基线与变更保留字节 + R2 list/get/put 与恢复读取 + 外部目的地存储/网络费用 + 演练环境 + 运维时间`。成本主因是变更率、旧版本保留和对象数，不只是邮箱当前容量；大对象全量日拷贝与对象增量策略分开比较。

### 7.1 配套恢复包与一致性

- 清单包含源 revision/构建、schema/迁移摘要、资源逻辑映射、D1 导出摘要与时间、对象 key/内容摘要/大小/恢复引用、密钥版本标识、配置版本及备份完成时间。报告不公开真实对象 key、账号/地址或凭据；实际清单加密私存。
- D1 与 R2 不存在跨服务事务。备份以可恢复 D1 点为基准，确保所有引用对象已保存；复制期间的覆盖/删除必须保留旧内容或进入协调快照窗口。仅 list + copy 或同步删除的镜像不足以保证一致恢复。
- 推荐增量对象日志/独立副本与周期导出配对，保护期与应用孤儿清理协调；启用前用并发修改、删除、备份中断验证。备份库不得被业务运行时写凭据删除。
- 密钥由操作者独立秘密管理系统保管，保留覆盖全部备份生命周期的历史版本。验证可取回并可解密受控 fixture；secret 绑定存在或格式正确不是可恢复证明。现有加密 key 轮换仍按原手册限制，不在本任务顺手轮换。
- KV 的认证/缓存/游标状态分开盘点：恢复时清缓存和撤销受影响会话/MCP 凭据，不能把 D1 回滚导致已撤销凭据复活。Queue/DLQ 不是备份；记录和核对存量及保留边界，重建只以恢复后的权威数据和外部事实为准。

### 7.2 隔离恢复流程及外部副作用保护

1. 演练先使用合成邮件和独立 D1/R2/Queue、独立域名及 mock provider；绝不在生产库演练。记录事故时刻与选定一致检查点。
2. 建立**不随待恢复 D1 一起回退的维护开关/恢复代际**，关闭 HTTP/MCP 写入、Email 接收写入、Queue 消费、Cron 修复、自动孤儿清理及 AI/发信提交。入站暂停期间的临时拒收/重试/旁路需明确验证，不得正常接收后丢弃；暂停 Queue 需保留消息，不能直接 ack 丢弃。
3. 保存事故时刻的新导出、D1 bookmark、资源/队列状态和当前外部提交证据，再恢复对象、匹配密钥、D1 和兼容代码/配置。Time Travel 原地操作仅用于已选定的受控恢复；隔离导入不假设 Time Travel 能直接克隆。
4. 自动核验 schema、外键/记录关系、所有必要对象的清单覆盖与摘要、受控加密数据解密、鉴权撤销边界和旧/新客户端。抽样读不能替代对象清单覆盖检查；大规模全字节校验时间需计入 RTO 或明确分阶段服务边界。
5. **D1 回退不会撤销已经发生的发信或付费推理。** 比对事故前保留的提交日志、服务商查询/回调和恢复点之后的活动；无证据的旧 queued/sending/AI attempt 一律隔离，不能重新执行。外部证据也必须在独立故障域保护，不能只存在同一份回退数据库。
6. 对 Queue 消息/入站重投/回调按恢复代际和幂等策略核对，防止旧消息触发重复工作。先开放只读校验，再开放安全写入，最后逐类恢复后台任务；未知外部结果继续冻结，不因其他功能恢复而自动重试。
7. 用批准的测试地址完成收取、查看、附件读取、发送和回调验收。记录完整服务恢复时间、实际数据缺口、隔离项数和副作用重复数；若未知发送仍冻结，需记录为降级恢复，不称完整 RTO 达标。

### 7.3 演练场景与通过证据

首轮至少覆盖 D1 误删/迁移回退、R2 单对象误删、错误/缺失历史密钥、备份中断、跨存储检查点不一致、Queue 重放，以及“外部发信/AI 成功但本地状态回退”。缺密钥或缺对象时必须明确拒绝宣布恢复成功。后续增加全资源重建和独立账号失效演练。

每次留存：合成数据 manifest 摘要、源/schema/资源代际、起止时间、最后完整检查点、恢复字节/对象覆盖、权限矩阵、外部调用次数、未解决项及改进动作。敏感清单/日志私存；仓库只保存脱敏 QA 结论。季度重复，以及数据模型、备份工具、加密方案有重大变更时重做。

以下是计划切片，不预分配已实施 CAP 或迁移编号。单个能力完成后再进入下一项，每项独立提交；只有选择目标安装后才能执行其远程验收。估时为一名熟悉代码的工程师的工作日粗估，不包含外部等待。

## 9. 必须覆盖的验收矩阵

| 场景 | 必须证明 | 层次 |
| --- | --- | --- |
| 同 key 同时发起，网页/MCP 交叉 | 最多一次上游提交、一次额度预占/结算 | 本地 Worker + 可控上游 |
| 不同用户竞争最后安装额度 | 不超安装总额，不发生半扣账 | 本地真实 D1 runtime 并发测试 |
| 同用户跨 mailbox/token 并发 | 用户上限统一生效，无身份/邮箱越权 | Worker 权限/竞争测试 |
| 刚好等于/超过输入、输出预占、周期额度 | 边界等值通过、超额在上游前拒绝；中英文/emoji/JSON schema 总量覆盖 | 单元 + Worker + 模型能力验收 |
| 午夜/月末、策略/模型变更、账户停用 | 原周期和原配置结算；权限撤销后不可读旧结果 | 可控时钟 + Worker |
| 上游已收请求后断线/超时/浏览器关闭 | 未知占用保留，不宣称取消计费，不自动二次推理 | 故障注入 + 受控 provider |
| 原生请求永不返回、isolate 被终止、迟到结果 | 未知容量受限；迟到结算一次；回调不运行也保持安全 | 本地故障注入；生命周期真实环境补证 |
| 正常响应后 D1/审计写入失败 | 原子回滚、保留安全占用、恢复不重新生成 | Worker 事务故障注入 |
| 拒答/截断/无效 JSON/正文过长 | 内容失败与 token 消耗分离，usage 不丢失 | 适配器 + 用例测试 |
| usage 缺失、价格未知、服务商超预占 | 不显示零消费；保守占用；超额停止模型准入并留下真实数字 | 单元 + Worker |
| 超过 24 小时的未知请求、过期重放 | 正文过期不清未知账；旧操作不被当新付费操作 | Worker 清理/迁移测试 |
| 旧 strict Web/MCP 客户端访问新服务 | 默认结构保持；协商未知值安全；新增错误不触发付费重试 | 冻结契约 + 旧构建浏览器 |
| 新客户端访问旧服务/代码回滚 | 降级明确；AI 治理不会被旧代码绕过；schema 兼容报告可复现 | 迁移 fixture + 版本矩阵 |
| 备份中对象修改/删除或任务失败 | 只有完整配套检查点可用；监控显示实际保护延迟 | 隔离集成/备份试验 |
| D1 恢复后旧发信/AI/Queue 重新出现 | 不重复发送、不重复付费、不复活已撤销凭据 | 隔离恢复演练 + 外部事实 fixture |
| 错 key、缺对象、缺外部提交证据 | 不宣布完整恢复、不自动放开发送 | 隔离失败演练 |
| 推荐规模整套恢复 | 记录可重现 RPO/RTO、对象覆盖、业务闭环、全部冻结项 | 已授权目标安装的隔离演练 |

实现改动按仓库要求运行 pnpm verify；上述 provider、跨版本浏览器和隔离恢复证据另行记录，不能由全绿测试代替。本轮仅文档，检查差异、链接、事实一致性与敏感信息即可。

## 10. 发布、回滚和下一步执行入口

- 先发布向后兼容的 schema/账本与观察能力，确认旧客户端和额度数据完整；设置策略后，仅对验证过的模型开启严格准入。观察期不得显示“硬额度保护已生效”。不凭观察期流量推断所有模型取消/计费语义。
- AI 治理关闭/回滚开关与秘密配置应独立于恢复快照。关闭治理不能变成无额度直通：回滚期间关闭付费入口，保留历史账本/未知处理。额度对账只纠正记账，不重新生成内容。
- 迁移先后顺序、维护开关、备份包、恢复证据有效期和旧构建支持范围进入 release manifest/checklist；脚本只验证可机械判定的条件，语义回滚与真实服务验收由 QA 证据补齐。
- 推荐下一实现切片是 **P1 冻结历史兼容测试 + P0 目标模型能力档案核对**，随后做 P2，避免先添加 quota UI 或修改 strict 响应。P3 严格启用依赖计数可信度；P6 外部操作依赖操作者指定安装/域名、测试地址及允许的费用/演练范围。
- 仍需在实施中确定：月/日 token 数值与默认并发、首批受支持模型及上界证明、保留容量、备份目的地/权限与数据规模、告警接收方式。用户已确定的额度模式不重复询问；告警消息发送与真实安装操作另按明确授权执行。

本轮交付是可执行计划及证据边界；没有修改 AI、接口、迁移、CI 或部署行为。
